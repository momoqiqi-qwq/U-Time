# v0.278.0 · 警大获奖名单加缓存新鲜期：6 小时内打开只画缓存，不再自动整轮重爬

> 接 v0.277.0。那一版把「每个请求」变便宜了（三连压两连、同步期不重绘、并发上限 16），
> 但**「每次点开这一页都自动跑一整轮」**没动 —— 而日常用法恰恰是一天点开好几次。

## 一、这一版的真正改动：让「打开」不再等于「重爬一轮」

`awStart()` 原本是无条件的：恢复缓存 → 画出来 → **立刻 `awSync()` 走完整轮**
（拉通知列表 → 逐条读正文 → 读附件 → 重新解析）。缓存只起到了「先给你看一眼旧的」，
用户仍然要等状态行爬完才算用完这一页。一轮下来一分钟起步。

现在加了一条新鲜期（`AWARD_CACHE_FRESH_MS = 6 小时`）：

| 情况 | 行为 |
|---|---|
| 有缓存、`syncedAt` 在 6 小时内 | **只画缓存就返回**，不建会话、不拉列表、不读正文 —— 秒开 |
| 有缓存但过期 / 没缓存 | 与以前一致，自动跑一整轮 |
| 用户点「刷新名单」/「再往前翻」/横幅重试 | 无条件放行（`awState.wantSync` 压过新鲜期） |

6 小时的理由：一天里多次点开都秒开，隔夜第一次进来会自动更新；而获奖名单本身就一个月才变几次。

## 二、连带必须处理的四处（漏一处就退回慢）

1. **状态行不能再说「已扫 N 条通知」**。缓存直出不拉列表，`state.notices` 是空的 ——
   沿用旧那句会读成「扫了 0 条」。缓存分支改成
   `本机缓存 · 奖项 N 人次 · 同步于 <时间> · 点「刷新名单」重新同步`，并早退。
2. **三个同步入口要自己建会话**。缓存直出时 `awStart` 根本没跑登录链，原来的
   `data-aw-sync` 直接调 `awSync()`（内部不建会话）就会先在 `awFetchList` 上撞一次墙。
   把 `awStart` 里那段「确保会话 / 否则摆出人工登录」抽成 `awEnsureReady(el)`，
   刷新、横幅重试、再往前翻三个入口都先过它。
3. **登录成功要记一笔「欠一次同步」**。`awEnsureReady` 的 `onDone` 置 `wantSync = true`，
   否则登录回来又被自己的新鲜期挡成「只看缓存」。
4. **「重新登录」按钮要显式置 `wantSync`**。它只清内存里的榜单，盘上的缓存（同一学号、同一口径）
   还能读回来，不清这一位就永远卡在缓存分支。

## 三、销账

`awSync()` 真跑完一轮（走到 `try` 块末尾）才把 `cacheOnly` / `wantSync` 归零；
走进 `catch` 不归零 —— 那一轮没成就还欠着，下次进来照旧要同步。

## 四、判定口径与落盘格式都没有动

`records` 结构、`AWARD_CACHE_VER = 2`、解析规则、候选集（`titleLooksAward()` 全量，不收紧）
一概不变 —— v0.277.0 那句「只让每个请求更便宜，不让该读的条目变少」在这一版同样成立。
缓存直接复用现有那份 `awardBoardCache`，不新增文件、不做迁移；旧缓存照常被新鲜期/版本号判定。
