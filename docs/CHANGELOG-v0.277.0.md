# v0.277.0 · 警大获奖名单同步提速：三连请求压成两连、同步期不再重绘空榜单、并发上限放到 16

> 用户反馈：「优化处理速度，感觉太慢了，有没有其他更快的方法」——截图是
> `正在读正文筛选获奖名单 47 条（本批 47/60 · 待读 164 条）· 并发 3`。

## 一、这一轮为什么慢：不是并发不够，是每条候选要等三次往返

v0.237.0 已经把「读正文」从串行 for 改成有界并发池（默认 3），但**每条候选内部**仍然是串行：

```
① getPimDetailInfoById  → ② CONTENT_URL 的正文页 → ③ getPimAffixList
```

门户单次 300~600ms，于是一条候选 = **1.0~1.6s**，而不是 0.3~0.6s。
211 条候选按并发 3 摊开就是 90 秒上下 —— 状态行上一格一格往前爬的那种观感。

而这三个请求的依赖关系只有一层：②要等①给出的 CONTENT_URL，**③只要 rid**。
原来的写法把它当成一条链排下来，白等了两个 RTT。

## 二、改了什么

| 位置 | 改动 | 效果 |
|---|---|---|
| `public/plugins/cppu-notify/main.js` `fetchNoticeContent()` | ③附件列表在函数入口就发出，与①详情并行；②正文页再与③并一层 —— 三连压成两连 | 每条候选省掉约 1/3 等待，**连普通通知视图的展开也一起变快**（同一个取数函数） |
| 同上 `awStatusOnly()`（新增） | 读正文 / 读附件两段循环里，进度刷新只重写状态行，不再 `awardPanel.render()` 整段重绘 | `awState.board` 在同步期仍然是**上一轮的榜单**，原来每读完一条就把一份完全没变的榜单重画一遍 —— 本机白烧 CPU、界面上还一路闪。这条同时也让「把并发调大」真的变快，而不是把时间花在渲染上 |
| `award-pool.js` / `settings/cppuAward.js` | 并发上限 `8 → 16`，档位 `[1,2,3,4,5,6,8] → [1,2,3,4,6,8,12,16]` | 瓶颈在对端 RTT，**并发是唯一能线性提速的手段**（在门户开始限流之前）。默认值仍 3：那是「对学校服务器礼貌」的那条线，不因为本机能跑就悄悄抬高 |

失败语义一条没动：①没了整条失败、②失败记 `contentError` 并回退 `PIM_CONTENT`、
③失败只记 `attachmentError` —— 两路互不影响、都能重试。

## 三、判定口径没动（重要）

候选集仍然是 `titleLooksAward()` 的全量结果，**没有收紧标题规则**。
`TITLE_SOFT` 里的「通知 / 公告 / 名单 / 公示 / 比赛」会让 3 年通知筛出 200+ 条候选，
看着很像「白读了一大半」，但那一页唯一不能出的错就是漏人 —— 用标题去砍候选等于拿准确率换速度。
所以这一版只让**每个请求更便宜**，不让**该读的条目变少**。

## 四、想更快还能做什么（未做，留档）

1. **详情落盘缓存**：现在 `state.details` 只活在本轮内存里，`saveNoticeCache()` 只缓存
   `PAGE_SIZE * PAGES_MAX`（前 500 条）通知的详情，而获奖同步会往回翻 3 年（往往 1000+ 条）。
   给获奖同步单开一份详情缓存，第二次打开就是秒开 —— 这是剩下最大的一块，但它要处理
   TTL 与「正文改过了」的判定，没跟这一版一起改。
2. **列表分页并行**：`awFetchList()` 是一页一页串着翻，翻 3 年约 20~40 页 = 10~20 秒，
   全在同步的开头。可以并发探页（拿不到 total 时要靠年份趋势猜页数），收益 10 秒级。
3. 门户如果开始限流（超时 / 429），把并发调回 1~3 更稳 —— 单条失败只会自己记一次失败，
   不再拖掉整轮。
